# 一、总体目标

# 三、长期记忆：必须实现完整闭环

## 3.1 数据分层

至少实现以下三类数据：

### L0：原始消息

保存用户和 AI 的原始消息。

包含：

- 用户 ID
- 会话 ID
- 消息 ID
- 消息角色
- 消息内容
- 创建时间
- 处理状态

原始消息不能被后续摘要操作随意覆盖。

### L1：结构化长期记忆

从聊天中提取有明确依据的重要信息。

例如：

用户说：

“上个月骑车摔倒，右膝盖受伤了。”

系统可以提取：

- 事件：骑车摔倒
- 身体部位：右膝盖
- 状态：受伤
- 时间：上个月，精度为月份或约略时间
- 来源：对应原始消息 ID

但不能凭空补充：

- 具体受伤日期
- 医院名称
- 医生诊断
- 伤情程度

### L2：事件与摘要

将有关联的记忆组织成生活事件。

例如：

- 受伤
- 恢复
- 后续活动

L2 可以作为后续扩展的能力，但必须保留与原始消息的关联。

未来更高级的个人画像、长期总结和多层压缩，可继续扩展，不能为了实现 V0.1 一次性引入过度复杂的架构。

## 3.2 记忆提取与更新

当用户发送消息时：

1. 原始消息首先可靠入库。
2. 判断是否包含值得保存的长期事实。
3. 使用结构化 Schema 提取候选记忆。
4. 校验提取结果和用户归属。
5. 保存来源、时间、类型和状态。
6. 根据现有记忆判断是否重复或冲突。
7. 更新相应记忆状态。
8. 新会话检索时只使用当前有效且允许使用的记忆。

例如：

用户之前说：“我的膝盖受伤了。”

后来又说：“我已经完全恢复了。”

系统不能永久保留一个仍然有效的“目前膝盖受伤”状态。

应当保留：

- 曾经受伤的历史事件。
- 当前已经恢复的最新状态。
- 两次信息对应的来源。

## 3.3 记忆必须支持用户控制

实现：

- 查看长期记忆。
- 查看记忆来源。
- 编辑错误内容。
- 删除记忆。
- 修改确认状态。
- 区分已经失效和当前有效的事实。

删除长期记忆后，不允许该记忆继续通过旧索引、缓存或摘要被跨会话召回。

同时明确说明长期记忆删除与原始聊天记录删除之间的区别。

# 四、批量模拟记忆：必须实现真实压力测试

这是本阶段非常重要的验收内容。

## 4.1 数据规模

至少生成：

**10,000 条结构化模拟记忆。**

不能只有 10,000 条重复的简单句子。

必须覆盖多样化内容，例如：

- 人物与亲属关系
- 工作经历
- 生活习惯
- 兴趣爱好
- 旅行经历
- 重要日期
- 健康相关的虚构经历
- 约会与日程
- 地点与生活事件
- 多年前的历史事件
- 一个月前的近期事件
- 状态发生变化的事件
- 有冲突或被纠正的信息
- 时间不确定的信息
- 信息不完整的记录
- 相似但并不相同的事实
- 已删除或已失效的记忆

时间跨度需要包含多年数据，用于模拟用户长期使用产品的情况。

## 4.2 数据生成规则

编写可重复使用的 Python 数据生成脚本。

必须支持配置：

- 用户数量
- 记忆数量
- 随机种子
- 时间跨度
- 事件类别
- 重复数据比例
- 冲突数据比例
- 无效数据比例

提供至少三档测试：

- 100 条：快速功能测试。
- 1,000 条：中等规模测试。
- 10,000 条：完整压力测试。

模拟数据必须标注为 Synthetic。

**模拟数据只能进入专门的开发或测试数据库，不能混入真实用户的生产记忆。**

禁止修改已有 `ALE_AI_MySQL` 数据库。

GitHub 只需保存生成脚本、少量固定测试样例及评估报告，不要提交包含隐私或巨大无必要数据文件的数据库导出。

# 五、记忆测试：不是入库成功就算完成

必须设计独立的 Memory Evaluation 测试体系。

至少包含以下测试。

## 测试 A：精确信息召回

模拟记忆：

“2019 年用户去过苏州旅游。”

问题：

“我是哪一年去苏州旅游的？”

预期：

准确回答 2019 年，并能引用对应来源。

## 测试 B：跨会话记忆

在会话 A 中提供事实。

关闭页面，重新登录并新建会话 B。

再次提问。

要求系统仍然能够检索相关记忆。

## 测试 C：语义改写

记忆：

“我以前在杭州工作过三年。”

问题：

“我曾经在哪座城市上过几年班？”

不能要求用户使用完全相同的关键词。

## 测试 D：矛盾记忆

旧记录：

“用户膝盖受伤。”

新记录：

“用户已经恢复。”

问题：

“我现在膝盖怎么样？”

必须优先使用当前有效状态。

## 测试 E：不存在的信息

问题：

“我去年 6 月 18 日中午吃了什么？”

如果没有相关记忆，必须承认不知道。

不允许编造答案。

## 测试 F：记忆删除

用户删除某条记忆。

重新开启会话。

被删除的长期记忆不能继续被召回。

## 测试 G：多用户隔离

创建至少两个独立测试用户。

用户 A 和用户 B 各自拥有大量模拟记忆。

用户 A 的检索结果不能包含用户 B 的私有数据。

## 测试 H：万级记忆性能

在至少 10,000 条记忆规模下：

- 执行批量检索。
- 记录检索耗时。
- 记录召回正确性。
- 记录数据库查询性能。
- 记录必要的内存和资源开销。
- 测试并发请求的基本稳定性。

不能将全部 10,000 条记忆直接拼接进每次 DeepSeek 的 Prompt。

必须使用真正的记忆检索与上下文选择机制。

# 六、评估指标与可视化报告

建立固定测试集，至少包含 200 条有明确标准答案的测试问题。

测试集应覆盖前述八类场景。

优先采用程序可以客观判断的标准答案；对开放式回答抽样进行人工复核。不能仅凭同一个 LLM 自我打分就声称准确。

至少输出：

1. Recall@5：正确记忆是否出现在前 5 个检索结果中。
2. Top-1 Accuracy：最相关结果是否正确。
3. Answer Accuracy：模型最终回答的事实正确性。
4. Hallucination Rate：没有证据却回答确定事实的比例。
5. Conflict Resolution Accuracy：矛盾记忆处理正确率。
6. Cross-user Leakage：跨用户数据泄漏次数。
7. Deleted Memory Recall：已删除记忆的错误召回次数。
8. Retrieval Latency：P50、P95 检索耗时。
9. API Latency：真实 DeepSeek 请求耗时。
10. Model Usage：token 与费用。

建议初始验收目标：

- Recall@5 ≥ 90%。
- Top-1 Accuracy ≥ 80%。
- 冲突状态判断正确率 ≥ 95%。
- 多用户数据泄漏次数 = 0。
- 已删除记忆的错误召回次数 = 0。
- 万级数据下本地 P95 检索耗时目标 ≤ 2 秒。

上述数值是本项目的工程目标，不是预先宣称能够达到的结果。

如果没有达到，必须保留真实结果，定位原因并迭代优化，不能更换容易的测试数据来制造通过率。

自动评估优先使用 Mock 模型或确定性测试。真实 DeepSeek 调用使用受控的小规模验证集，记录实际费用，避免万级数据测试导致不必要的 API 成本。

最终生成可阅读的 HTML 测试报告和原始指标文件，展示不同数据规模下的性能和正确率。

# 七、记忆检索架构要求

采用可扩展的接口设计。

至少抽象出：

- MemoryExtractor：记忆提取。
- MemoryRepository：持久化存储。
- MemoryRetriever：记忆检索。
- MemoryUpdater：记忆更新与失效。
- ContextBuilder：构建模型上下文。
- MemoryEvaluator：记忆质量评估。

初期可以通过 MySQL 结构化查询、关键词搜索等方式建立基线。

如果实测表明大量记忆的语义召回不足，再考虑引入 Qdrant 等向量检索组件。

不要为了追求技术栈复杂而提前引入多 Agent、多数据库、多套消息队列。

如果引入向量索引：

- MySQL 仍然是事实数据的主要存储源。
- 向量索引视为可重建的派生索引。
- 用户 ID 过滤必须在检索阶段生效。
- 编辑、删除、失效后应同步更新索引。
- 需要测试索引重建及故障恢复。
