## 0. 决策摘要（给 Codex 先看）

用户明确提出：产品不能只是聊天、保存经历与回忆，还需要在现实生活中**主动而可靠地帮助用户完成事情**。

以下功能由 V0.1 后续功能/手动站内提醒调整为 **V0.1 核心验收 P0**：

1. 用户在自然对话中口头/文字提出“明天几点去哪里，记得提醒我”。
2. 系统识别这是可执行任务，提取时间、目的地、出发点、交通方式等；缺信息时只追问必要字段。
3. 给用户展示一张**真实可编辑、确认后落库**的出行任务卡。
4. 查询路程/预估耗时、天气预报，估算出门时间与需要提醒的时间；需要时提醒带伞。
5. 使用持久化任务调度器到时间主动发送提醒；本机重启/服务重启后任务不会凭空消失。
6. **至少在一台真实 Android 手机上**验证 App 退到后台/关闭页面后实际能收到提醒；PC H5 仍是开发和 UI 验证环境。
7. 如定位权限拒绝、地点不明确、API 失败，也必须至少可以保存一个时间明确的普通提醒，不得假称路线已计算、通知已送达。

与上一版不同：**“任务已记录”与“通知真正送达”是两件事，必须分别可观测、可验收。**

## 1. 重新定义产品

产品定位：**“有长期记忆的 AI 生活助理，同时帮用户保存人生故事。”**

核心价值分两条：

- **生活执行闭环**：用户随口提出意图 → AI 理解 → 自动查证/计算 → 可靠安排 → 主动通知 → 用户采取行动。
- **人生记忆闭环**：聊天记录 → 提取有来源的事实/事件 → 跨会话检索 → 回忆展示/纠错。

优先级：对 V0.1 Demo，**前者至少完成一个可用的真实出行提醒链**，与跨会话记忆并列 P0。照片/视频重现仍延期，语音方言识别作为后续高价值模块，不在本次变更强行引入。

## 2. 用户故事与人机交互

### 2.1 示例：老人说明天去做客

用户：
> 明天上午 10 点我要去城西张阿姨家做客，记得提醒我呀。

系统先理解：用户是否想“10 点到达”还是“10 点出发”？“张阿姨家”是否已有用户**明确授权保存**的地点？从哪里出发、采用什么交通方式？

若必要信息缺失，只追问缺失项：
> 好的，我帮你记下。您说的“10 点”是希望 10 点到达吗？张阿姨家的位置我还不清楚，方便选一下地址吗？您打算坐公交还是打车？

用户确认：
> 10 点到，打车，从我家出发。

仅在获得地址/地点确认和位置使用许可后，服务端查询路线及天气；例如**以下数字均为演示假设，不能当成实时查询结果**：

- 计划到达：10:00
- 估计车程：35 分钟
- 叫车/走路：10 分钟
- 弹性缓冲：15 分钟
- 建议出门：09:00
- 用户偏好：出门前 30 分钟提醒 → 08:30 推送
- 天气：预报可能有雨 → “建议带伞”，注明来源和更新时间

聊天回复不应只有文字承诺，还必须显示真正的可编辑确认卡：

```text
┌────────────────────────────────┐
│ 明日出行提醒 · 待确认           │
│ 事项：去张阿姨家做客            │
│ 目的地：城西 XX 小区 [修改]     │
│ 目标：10:00 前到达 [修改]       │
│ 交通：打车 [修改]               │
│ 预计车程：约 35 分钟            │
│ 建议出门：09:00                │
│ 提醒时间：08:30 [修改]         │
│ 天气：可能有雨，建议带伞        │
│ [确认并保存] [稍后再说]         │
└────────────────────────────────┘
```

点击“确认并保存”→ MySQL 出行任务/提醒落库 → 后台调度成功 → UI 显示“已安排 08:30 提醒”，同时显示通知授权状态。**禁止把 LLM 的“好的，我明天提醒你”直接当成安排成功。**

### 2.2 出行前的主动行为

- T-24h：任务已确认，系统保存地点/交通方式；可以有初步天气预报和路线参考。
- T-2h（可配置）：刷新路线与天气数据；如 API 失败继续保留原提醒。
- T-30min before estimated departure（用户可修改）：发一次主要通知。
- 若路况使建议出发时间变化超过明确阈值（如 10 分钟），且通知权限存在，可发一条“出门建议有变化”的更新，控制频率。
- 用户点击通知：打开“本次行程”页面，展示事件详情、导航入口、任务操作。
- 用户选择“已出发”“完成”“不去了/取消”，后续任务和重复提醒按状态正确停止。

**时间语义不能混淆：**“明天 10 点出门”与“明天 10 点到那里”完全不同；对不明确表述必须澄清。

### 2.3 缺省和降级策略

| 情况 | 系统应如何处理 |
|---|---|
| 未说明目的地 | 询问具体地点；可以先创建普通定时提醒 |
| “明天几点”有歧义 | 按设备/用户时区结合当地日期解析，歧义时确认 |
| 用户拒绝位置权限 | 可手动输入出发地；无法计算则只做普通提醒 |
| 不知道交通方式 | 询问或用用户已经确认的偏好，不能自行确定 |
| 地图 API 失败 | 显示“暂无法估算车程”，不影响纯提醒保存 |
| 天气 API 失败 | 不给虚假天气判断，仍发送出门提醒 |
| 交通变化大 | 重新估计并有限通知，不每分钟打扰 |
| 系统通知未授权 | 显示显著提醒“不保证离开应用后收到通知”，给出开启权限入口 |
| APP 关掉后 | 真实手机上通过已配置的离线推送渠道尝试提醒，并追踪送达状态 |
| 无网/系统限制导致推送失败 | 留下可见失败状态与站内提醒，不能标记“已送达” |
| 任务修改或取消 | 更新或取消未来待发调度，避免残留旧通知 |
| 一句话提到多个安排 | 逐条抽取并分条确认，防止混合时间与地点 |

## 3. 先解释“真能提醒”的技术现实

### 3.1 H5、微信小程序、App 区别

| 平台 | 能否用 PC 快速调试 | 关闭页面后可靠系统通知 | 本项目用途 |
|---|---|---|---|
| uni-app H5 网页 | 可以 | 不能依赖普通页面计时器保证；具体 Web Push/浏览器/权限还需单独验证 | V0.1 主要开发、交互与后端联调 |
| 微信小程序 | 可以用微信开发者工具 | 受用户订阅、模板及微信规则约束，不是任意发 | 未来可用路径，需单独验证 |
| uni-app Android App | 可以从同一前端工程打测试包 | 可集成离线推送，仍受厂商、权限和设备状态影响 | **V0.1 至少一台真机验证** |
| iOS App | 需苹果推送证书/权限 | 可接入 APNs 等，但有系统策略和上架开发成本 | 暂不强制 |

uni-push 2.0 官方明确 App 端支持厂商离线通道；小程序/Web 的在线与离线能力、权限要求不同。参考：https://uniapp.dcloud.net.cn/unipush-v2.html 。

**不可保证 100% 送达**：系统可能关通知、手机没电/断网、厂商限制。产品应如实告知，并提供提醒授权引导、通知发送状态、错过任务后的可见入口。若未来定位“绝对不能错过”的高风险提醒，需要经同意的短信/电话等备用通道与更严格 SLA，不能把 V0.1 的普通推送当生命安全保障。

### 3.2 路程估算不是准确预言

- 路线由地图 API 返回预估路程与耗时，可能随时间、拥堵、天气变化。
- 提前一天获得的值应标“参考”；临近出门需再次查询。
- 天气预报通常是区域/时间段估计；“建议带伞”只在有可用预报证据时出现，不能凭模型想象。
- 雨具、出发缓冲等应个性化且可修改，不应强制按照产品建议出门。

| 日志/测试 | pytest、Playwright 等 | 开源，具体版本核对 | 全 Mock 自动测试 + 少量真实联调 |

## 5. 必须新增/调整的数据模型

沿用 `users/conversations/messages/memory_facts/reminders`，新增：

- `outing_tasks`：`id, user_id, source_message_id, title, status, arrival_at, arrival_or_departure, timezone, destination_text, destination_place_id, destination_lat/lng, origin_type, origin_lat/lng, transport_mode, estimated_travel_seconds, pickup_walk_buffer_seconds, contingency_buffer_seconds, recommended_departure_at, reminder_at, user_confirmed_at, created_at, updated_at`。
- `place_aliases`（可选第一版轻量实现）：用户授权定义的“我家”“张阿姨家”与地点关联；可编辑/删除；不得根据对话自行推断真实住址。
- `route_weather_snapshots`：`outing_id, provider, fetched_at, route_duration_seconds, distance_meters, weather_summary, forecast_for_at, raw_reference_code`；不要长期无必要保存精确位置/完整供应商原始响应。
- `notification_jobs`：`id, user_id, outing_id, channel, scheduled_at, status, retry_count, idempotency_key, provider_message_id, last_attempt_at, error_code`。
- `notification_devices`：`id, user_id, platform, push_client_id, permission_status, last_seen_at, revoked_at`；设备标识加密/限制读取，不上传 Git。
- `task_audit_log`：任务创建、用户确认、变更、调度、推送尝试、用户查看、取消等不可混淆的事件状态。

这些字段只是合同示意；Codex 应设计主外键、索引、Alembic 迁移、用户隔离和历史状态，并保证原有 `reminders` 与新 `outing_tasks` 的关联一致。

## 6. 计算规则（确定性代码负责，而非靠 LLM 猜）

用户说“明天 10 点到达”，出门时间为：

```text
recommended_departure_at
  = arrival_at
  - estimated_travel_duration
  - pickup_or_walk_buffer
  - uncertainty_buffer

notification_time
  = recommended_departure_at
  - preferred_advance_notice
```

示例：10:00 - 35 分钟车程 - 10 分钟叫车/步行 - 15 分钟缓冲 = 09:00 建议出门；08:30 提醒。

要求：

1. 由 DeepSeek 提取**字段与意图**，由 Python 负责时区、运算、校验、调度。
2. `arrival_or_departure` 必须显式保存；不能把“几点去”默认一定是到达。
3. 用户可编辑缓冲与提前提醒分钟数，偏好须显式设置和可撤销。
4. 最晚建议出门早于当前时间时，立即告知可能来不及，并要求用户调整。
5. 地图返回误差/超时或建议不确定时展示区间或“参考”，不能给虚假精度。
6. 任务入库、job 入库/变更尽可能通过一致的事务/可靠 outbox 实现；调度端通过唯一 idempotency_key 避免重复推送。
7. 通知 Worker 启动后重扫待发任务，处理停机期间错过的提醒，并明确“已过时不再机械发送无意义提醒”的策略。
8. 消息投递状态区分 `queued/sent_to_provider/delivered_if_confirmed/failed/opened`，缺平台回执不能写“已送达”。
9. 若第三方通知发送失败，采用有限次数重试，不能无限轰炸用户。

## 8. 新增任务拆分及 GitHub 记录

**请调整既有 T00–T14 合同：T00–T10 仍按原计划，T11 从“手工站内提醒”变更为以下子任务。** 在 T01 起预留表与服务边界，在 T11 实作。不得改写历史已完成任务；将变更记入 ADR、CHANGELOG、TASK_STATUS。

| 任务 ID | 新任务 | 验收 |
|---|---|---|
| T11A | 自然语言任务识别与确认卡 | “明天 10 点去做客”可解析/追问，用户确认后才创建 |
| T11B | 高德地点、路线与天气集成 | 真实 Provider + Mock；路线/天气失败能降级 |
| T11C | 推荐出门时间与持久化调度 | 服务器重启后仍可送到待发状态；修改/取消生效 |
| T11D | 真实手机提醒交付 | Android 测试包装载，授权后退到后台/关闭页面收到通知；记录发送与实际观察结果 |
| T11E | 行程详情与用户反馈 | 可见来源/路线/天气/通知状态；可取消、编辑、完成 |

### 8.1 扩展 T13/T14 的验收

必须新增以下端到端场景：

1. 用户 A 说“明天早上 10 点到张阿姨家”，未明确地址 → 系统提问、无擅自安排。
2. 用户 A 补地址和交通方式 → 显示到达时间、预计车程、建议出门时间、预估提醒时间。
3. 用户点击确认 → 刷新/重新登录仍可看到已安排的真实任务。
4. 用户修改地点/时间 → 旧 job 被取消/失效，新的时间正确；数据库不得存在同时有效的重复 job。
5. 用户取消出行 → 不再收到旧提醒。
6. 地图、天气都不可用 → 仍能保存明确时间的普通提醒，不编造路程或雨情。
7. 模拟服务器重启和错过时间窗口 → job 可恢复/正确处理，不重复群发。
8. 同一出行任务重复请求 → 不产生重复任务或多条无意义通知。
9. 账户 B 查询账户 A 的行程和通知记录 → 被拒绝。
10. 手机 Android App 真实测试：用户给予通知权限，App 关闭/后台，测试设为几分钟后提醒，手机实际收到通知；截图/屏幕录制仅使用合成数据。
11. 用户拒绝通知权限 → UI 清晰告知“离开应用后可能无法提醒”，不假装成功。
12. 天气变化与路程变化触发阈值与频率控制，可关闭主动变更提醒。
13. 日志、Git 历史中没有地图私钥、推送凭据、真实家庭地址。

## 9. UI 重新聚焦

主界面继续采用你喜欢的 **Muse 式中心对话**，让 AI 输出/聊天占据大部分空间，底部宽大的文本输入、未来扩展语音按钮；温暖米白 + 常青绿视觉系统不变。

新增三种关键可操作卡片：

1. **待确认任务卡**：地点、时间、交通、提前量，每项可点开修改；突出“确认提醒”按钮。
2. **明日行程卡**：建议出门时间为最大文字；路线时间、天气、带伞建议、导航入口。
3. **通知状态卡**：待发送/已提交到服务商/已确认到达（如有回执）/失败，显示测试真实状态而非编造绿勾。

适老交互：

- 文案具体，例如“明早 8:30 提醒您出门”，不要写“Agent 已调用工具”。
- 信息不明宁可多问一句，避免提醒错日、错地址。
- 用户可以说“改成下午 3 点”“不用提醒了”，系统应找到关联任务并二次确认高影响变更。
- 尽量把“一次授权可复用的偏好”保留为显式可撤回设置（常用出发地、交通偏好、提醒提前量），不是替用户默默推断。
